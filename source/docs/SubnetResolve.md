# SubnetResolve

Запуск (Bash и curl):

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/NNN706/M3T/test/source/SubnetResolve.sh) -4s https://visor.sberbank.ru/get api-web.samokat.ru
```

Домены и HTTP(S) URL указываются через пробел. Без аргументов скрипт спросит их. Из URL автоматически извлекается домен.

- `-parse` — открыть сайты в фоновом Chromium, собрать домены запросов (включая сторонние) и выполнить DNS → BGP. С `-4` вывод: `{"domain":["domain:example.com"],"ip":[...]}`.
- `-4` — один JSON `{"ip":[...]}` с уникальными IPv4-подсетями всех доменов.
- `-s` — без вопроса о сохранении и без файла.
- `-v` — подробный журнал и полные данные узлов.

По умолчанию прогресс обновляется одной строкой; сохранение в `resolved.json` — по запросу, default **no**. Недостающие зависимости устанавливаются через доступный пакетный менеджер.

JSON — в stdout; ссылки отчётов и ошибки с доменом, узлом, страной и причиной — в stderr. При неполном результате выводится причина и пояснение, какие данные доступны. Для автоматизации сохраняется ненулевой статус завершения. В полном формате несколько доменов находятся в массиве `domains`, каждый со своим `permanent_link`.

Открытие сайтов через curl — до 2 секунд на попытку; Check-Host — до 1,5 секунды, в одном цикле две попытки; опрос готовности DNS-отчёта — до 60 секунд на домен. Внутренний DNS-тайм-аут удалённых узлов задаётся самим Check-Host.

Пример сбора доменов сайта:

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/NNN706/M3T/test/source/SubnetResolve.sh) -parse -4s samokat.ru
```

Первый `-parse` устанавливает Node.js/npm при отсутствии, Playwright 1.64.1 и Chromium; нужен Node.js ≥20. Повторные запуски используют кеш. Один экземпляр Chromium обрабатывает до двадцати исходных сайтов одновременно, каждый в отдельном контексте. Браузер ждёт загрузку до 30 секунд и прокручивает страницу 10 секунд; это отдельные лимиты от DNS/BGP. Вход, выбор города и переходы по ссылкам не выполняются. Список отражает наблюдаемые запросы, включая неудачные, а не все возможные домены сайта. Отказ сайта в доступе и ошибки загрузки объясняются словами; доступные результаты сохраняются. В полном `-parse` JSON массив `domain` содержит правила, `domains` — результаты DNS/BGP, `discovery` — данные сбора.

Перед Chromium сайт проверяется через curl. Недоступный сайт пропускается, остальные обрабатываются. Перед DNS проверяется API Check-Host, перед BGP — маршрут 1.1.1.1 через BGP.tools; при тайм-ауте Check-Host зависимые этапы ждут восстановления API; другие ошибки сервисов объясняются отдельно.

CI запускается при изменениях в `test` на раннере `Admiralteskiy`. Тест поднимает локальный сайт с шестью доменами `*.localhost`, проверяет Chromium, JavaScript, iframe, WebSocket, прокрутку и понятное сообщение об отказе в доступе. DNS/BGP подставные: внешние сайты и Check-Host для этого теста не нужны. Журнал и результаты доступны в артефактах GitHub Actions.

Матрица отказов проверяет два рабочих адреса, рабочий + нерабочий, обратный порядок и два нерабочих адреса на этапах curl, DNS и BGP, повторные попытки и отсутствие лишних последующих запросов.

Check-Host: первая попытка — TLS 1.2; после тайм-аута или ошибки TLS вторая использует обычное согласование. После HTTP/JSON-ошибки повторяется TLS 1.2. Каждый новый запрос снова начинается с TLS 1.2; сертификаты проверяются. `-v` показывает режим и причину повтора.

HTTP(S)-редиректы сайтов отслеживаются автоматически, включая переходы на другой домен; цепочка имён хостов (например, `mc.yandex.ru → mc.yandex.ru`) выводится только в stderr, без путей и параметров URL. Предел — 50 переходов для защиты от циклов. Лимит 2 секунды действует на всю цепочку одной попытки открытия сайта. При ошибке указываются конечный HTTP-статус, проблема подключения/TLS или истечение лимита; редирект сам по себе не считается ошибкой.

При тайм-ауте API Check-Host после двух попыток скрипт ждёт 5, 10, 20, затем по 30 секунд и повторяет тот же запрос до восстановления связи (остановка — `Ctrl+C`). После восстановления продолжает текущий домен; время восстановления не расходует лимит опроса DNS. Ответ узла без IP или с DNS-ошибкой считается окончательным: новый DNS-запрос для него не запускается. Опрос общего отчёта продолжается только ради ещё не ответивших узлов.

BGP.tools обрабатывает до 100 IP в пакете: до 10 секунд без данных и до 30 секунд на пакет, с завершением сразу после получения всех ответов. BGP.tools возвращает BGP-префикс (подсеть, содержащую IP) и ASN анонсирующей автономной системы. При TCP-тайм-ауте/ошибке соединения — ожидание 5/10/20/30 секунд до восстановления либо `Ctrl+C`. Уже полученные записи сохраняются; повторно отправляются только IP без ответа. Явный ответ без префикса/ASN или с некорректными данными сообщается отдельно, без бесконечных повторов. WHOIS Bulk: https://bgp.tools/kb/api .

Проверка сайта в обычном терминале обновляет одну строку: попытка, редирект и итоговый статус. `-v` оставляет одну завершённую строку на попытку. В CI есть отдельный live-тест `cloud.vk.com → cloud.vk.ru`: curl (15 секунд) и настоящий Chromium должны получить HTTP 200; результат штатного preflight 2 секунды сохраняется отдельно в артефактах.

В обычном режиме браузерные редиректы скрыты: для каждого сайта остаётся один итог `найдено доменов: N`. Ожидание и восстановление API/BGP обновляют текущую строку; отдельные промежуточные сообщения сохраняются только с `-v`. При перенаправлении stderr промежуточный прогресс не печатается.

Правила по исходным сервисам: `bash <(curl -fsSL https://raw.githubusercontent.com/NNN706/M3T/test/source/SubnetResolve.sh) -parse -rules -s samokat.ru selectel.ru`. Вывод: `{"rules":[{"ruleTag":"samokat.ru","ip":["109.238.88.0/24"]},...]}`. Это фрагменты правил: добавьте свой `outboundTag` или `balancerTag` перед использованием в Xray. `-4` сохраняет прежний формат. Ответы DNS-узлов без IPv4 показываются в stderr только с `-v`; полнота результата и статус завершения сохраняются.

Workflow **Update service routing prefixes** запускается вручную из ветки `test` или при изменении `source/routing/sites.txt` в `test`. Файл: домены/URL через пробел либо по одному на строке, комментарии `#`. Генератор сохраняет JSON правил в `source/routing/generated/IP.json`, удаляет повторы и объединяет совместимые соседние подсети между всеми сервисами без расширения набора адресов. При неполном сканировании workflow сохраняет доступные данные и объединяет их с прежними подсетями соответствующих сервисов. Пустые новые результаты не удаляют прежние правила. Неполнота отмечается предупреждением и отчётом в артефактах routing-evidence. При полном отказе, некорректном JSON или отсутствии пригодных подсетей прежний файл сохраняется. Каждая итоговая сеть присутствует ровно в одном правиле IP.json; её исходные сервисы сохраняются в sources.json. Workflow коммитит `IP.json`, `domains.json` и `sources.json` в `test`; `main` не меняется.

Перед публикацией workflow получает актуальный `test` и создаёт коммит поверх него. Изменения других файлов сохраняются; при гонке push повторяется до трёх раз без force. Если за время сбора изменились сканер, генератор или прежний `IP.json`, устаревший результат не публикуется — он остаётся в артефактах, включая готовый `IP.json`.

Результаты update: `source/routing/generated/IP.json` — правила `ruleTag`/`ip`, `source/routing/generated/domains.json` — отдельные правила `ruleTag`/`domain`. Оба файла и sources.json публикуются одним коммитом и сохраняются в артефактах. Полные домены каждого исходного сервиса, включая сам сервис и запросы браузера, сохраняются в sources.json → domain_observations; domains.json содержит сокращённые правила с тем же покрытием. При неполном сборе сохраняются прежние данные. ASN задаются в `source/routing/asn.txt`.

Старый `source/ip/IP.txt` разово объединён с результатами сканирования: совпадающее покрытие исключено, остаток сохранён под `ruleTag: legacy`, IPv6 сохранены. Совместимые подсети объединены без добавления адресов; принадлежность общих CDN-сетей сохраняется в sources.json. Workflow не импортирует старый список повторно и сохраняет legacy при следующих обновлениях.

IP.json теперь объединяется глобально между всеми ruleTag: каждый итоговый CIDR записывается ровно один раз, под первым по алфавиту тегом из участвовавших сервисов. Теги становятся условными группами хранения; направление трафика у них должно совпадать. sources.json сохраняет исходную принадлежность сетей сервисам и публикуется вместе с IP.json и domains.json. Перед записью проверяются точное равенство адресного покрытия и отсутствие пересекающихся итоговых сетей.

Удаление: при полном успешном сборе прежние подсети, которые больше не найдены, удаляются; при неполном сборе сохраняются и объединяются с новыми. Удаление сервиса из sites.txt удаляет его вклад, но сохраняет адреса, найденные у других сервисов. Импортированные legacy-сети остаются постоянными. Полный отказ или пустой результат не затирает прежние файлы.

В инкрементальном Update Check-Host опрашивает до 15 доменов одновременно.
Если снимок BGP.tools содержит более широкий анонс того же ASN, Update
использует его для итоговых IP-правил. Например, при вложенных /24 и /15
выбирается /15. В completeness.json отдельно перечисляются домены без
префикса из-за исключений ASN и причины неполного DNS/BGP.

Ручные CIDR задаются в `source/routing/ip.txt`, по одной подсети на строку.
Разделы `#### Локальные подсети` и `#### Остальные подсети` помогают ориентироваться;
ASN-исключения применяются к обоим разделам. Заголовки и комментарии `#` не влияют на маршрут.

Специальные разрешения поверх ASN-исключений задаются в `source/routing/config/manual.txt`:
заголовок `#### ruleTag`, затем CIDR по одному на строку. Здесь сохраняются две разрешённые Amazon /24.

Update публикует IP.json, domains.json, sources.json и собранный
Templates/Routing-(RU-Direct)/routing-ru.json одним коммитом. IP-правила
активны с outboundTag direct, доменные правила с тем же outboundTag записаны
в комментариях. Следующий Xray-job проверяет SHA опубликованной конфигурации.

## Файлы маршрутизации

Все списки для редактирования находятся в [routing](../routing/):

- [sites.txt](../routing/sites.txt) — сайты и домены для сбора.
- [ip.txt](../routing/ip.txt) — ручные CIDR direct, включая legacy; ASN-исключения применяются.
- [domains.txt](../routing/domains.txt) — ручная основа общих доменных правил, включая группу main.
- [asn.txt](../routing/asn.txt) — ASN для выгрузки анонсов.
- [exclude.txt](../routing/exclude.txt) — исключённые ASN.
- [asn-report-full.md](../routing/asn-report-full.md) — общий отчёт с подсетями и DNS-наблюдениями.

`routing/generated/` содержит итоговые `IP.json` и `domains.json`; `routing/state/` —
исходную принадлежность сетей и DNS-наблюдения. `routing/config/manual.txt` задаёт
адресные разрешения поверх ASN-исключений. Код сборки и публикации — в
`routing/scripts/`, тесты — в `tests/`, проверки Xray — в `tests/xray/`.

Изменения sites.txt, ip.txt, asn.txt, exclude.txt или config/manual.txt запускают Update в test.
Пустые строки и комментарии `#` разрешены в ip.txt. Указывайте CIDR с корректным адресом сети.
Краткий ASN-отчёт отдельным файлом больше не публикуется.

Целиком покрытые сетями сервисов ручные CIDR удаляются из ip.txt и legacy в sources.json.
Частично покрытые блоки остаются целыми. Итоговый IP.json по-прежнему объединяется
глобально без увеличения адресного покрытия; при выборе группы хранения сервис имеет
приоритет над legacy. Точная принадлежность частей объединённой маски сохраняется
в state/sources.json и полном отчёте, а ruleTag итогового IP.json обозначает группу хранения.

IPv4 сетей Hetzner ограничены наблюдавшимися /24 через
`routing/config/prefix-limits.txt`. Update использует текущие DNS-IP и
`routing/state/dns-provenance.json`, поэтому ограничение сохраняется при
инкрементальном и ежедневном полном сборе. Широкий ASN не разворачивается
целиком в набор /24. Изменение prefix-limits.txt автоматически запускает Update.

Общие full:/domain:/keyword: задаются в routing/domains.txt по секциям #### ruleTag.
Update дописывает только непокрытые наблюдения, удаляет пустые группы и сохраняет
полный явный список для DNS в sources.json → domain_observations. Доменные правила
в routing-ru.json остаются комментариями. Изменения domains.txt запускают Update.
